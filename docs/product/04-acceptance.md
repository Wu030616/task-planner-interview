# 验收案例

规则、决策和文案编号（R、D、S）见[方案](01-solution.md)；任务编号（T）和接口约定见[任务拆解](03-tasks.md)。

## 怎么观察

| 观察什么 | 怎么看 |
|---|---|
| 模型调用次数 | 服务端日志里 `mock-ai.started` 的条数，一条代表一次计费调用；同一次调用的 `started` 与 `succeeded` 或 `failed` 共用同一个 `callId` |
| 接口返回 | HTTP 状态和错误类型，取值见 03 的[接口约定](03-tasks.md#接口约定) |
| 余额 | 数据库 `User.credits`（`wasp db studio` 或 SQL）；页面右上角"剩余额度" |
| 日程数 | 数据库中该用户的 `PlanResult` 条数；页面上的历史日程 |
| 准备数据 | 用 `wasp db studio` 或 SQL 把测试账号余额设为指定值；描述含 `[fail]` 的任务会让模拟接口明确失败（见 [README](../../README.md)） |

除非另有说明，每条案例的前置条件都包含：1 条普通任务，时长为默认的 8 小时。

## 不变量

每条案例都要满足：

- I1：所有请求结束后，余额不小于 0。过程中不出现负数，由 T8 的数据库约束保证。
- I2：所有请求结束后，初始余额减去最终余额，等于新增日程数。
- I3：每次请求结束后，不刷新页面，右上角余额就与数据库一致。

| AC-02 | 余额为 0 时打开页面 | 余额 0；至少 1 份历史日程 | 打开页面 | 生成按钮置灰；显示 S4（暂不支持充值、联系管理员）；历史日程可见；没有发出生成请求 |
| AC-03 | 余额为 0 的请求到达服务端 | 余额 0 | 绕过页面直接调用生成接口 | 返回 402 / `NO_CREDITS`；`started` 0 条；余额 0；新增日程 0 |
| AC-04 | 页面收到"没有可用额度" | 余额 1；接口被模拟为返回 402 / `NO_CREDITS`（前端测试，或用浏览器开发者工具改写响应） | 点击"生成日程" | 显示 S5；不出现英文技术报错 |

| AC-07 | 保存失败 | 余额 3；测试环境开启保存失败注入（T9） | 点击"生成日程" | 返回 500 / `SAVE_FAILED`；`started` 1 条、`succeeded` 1 条；余额仍为 3；新增日程 0；页面显示 S7 |

## 并发

AC-08 至 AC-10 由并发验证脚本执行（T7），要求见[并发验证要求](#并发验证要求)。AC-11 在页面上手动验证。

| ID | 场景 | 前置条件 | 操作 | 预期结果 |
|---|---|---|---|---|
| AC-08 | 余额只够 1 次 | 余额 1 | 同一账号同时发出 3 个生成请求 | `started` 恰好 1 条；1 个返回 200，2 个返回 402 / `NO_CREDITS`；余额 0；新增日程 1 |
| AC-09 | 余额够 3 次 | 余额 3 | 同一账号同时发出 5 个生成请求 | `started` 恰好 3 条；3 个返回 200，2 个返回 402 / `NO_CREDITS`；余额 0；新增日程 3 |
| AC-10 | 余额只够 1 次，模型失败 | 余额 1；唯一的任务描述含 `[fail]`；3 个请求都在第一个请求返回之前到达 | 同一账号同时发出 3 个生成请求 | `started` 恰好 1 条，以 `failed` 结束；1 个返回 502 / `MODEL_FAILED`，2 个返回 402 / `NO_CREDITS`；余额回到 1；新增日程 0 |
| AC-11 | 快速连点 | 余额 3 | 在页面上快速连点两次"生成日程" | 只发出 1 个请求；`started` 1 条；余额 2 |

AC-10 的结果取决于到达时间：按 D3，第一个请求进行中到达的请求立即被拒；如果某个请求在额度退回之后才到达，它会正常冻结并调用模型，这也符合设计。所以脚本要先确认前置条件，见下文第 5 条。

## 并发验证要求

给 T7 的要求：

1. 每次运行前，把测试账号余额设为案例指定值，并记下该账号已有的日程条数。
2. 登录拿到会话，然后同时发出 N 个生成请求，不能一个接一个地发。记录每个请求的发出时间和返回时间。
3. 收集四项结果：每个请求的 HTTP 状态和错误类型，这段时间内 `mock-ai.started` 的条数，最终余额，新增日程条数。
4. 运行期间不要有其他生成请求。`mock-ai.started` 日志里没有用户信息，只能按时间段统计；有了 T10 的日志后，可以按用户交叉核对。
5. AC-10 先检查前置条件：所有请求都在第一个请求返回之前到达。不满足就标记为"前置条件不满足"并重跑，不算失败。
6. 逐项与上表比对，输出通过或不通过。每个案例连续运行至少 3 次，结果完全一致才算通过。
